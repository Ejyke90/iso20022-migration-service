P0 Pipeline Classification

Use this decision tree to self-assess before requesting P0 priority protection. Registration must happen proactively — not during an active Red event.
Step through the questions below
Question 1 of 5
Does this pipeline deploy directly to a production environment — or a pre-prod environment that feeds production within 24 hours?
Question 2 of 5
Is this pipeline required to satisfy a regulatory, audit, or compliance obligation?
Examples: mandatory SAST/DAST gate, SOX control evidence, vulnerability scan required before any merge.
Question 3 of 5
Would a delay of more than 2 hours cause direct financial impact, an SLA breach, or measurable reputational harm to the institution?
Question 4 of 5
Is this pipeline part of an active incident response or a hotfix for a live production issue right now?
Question 5 of 5
Has this pipeline been formally registered with the DevOps team as a named P0 pipeline in the service catalogue?
P0 — protected during load shedding
This pipeline qualifies for P0 status
P0 pipelines run even when Red tier load shedding is active. Production deploys, mandatory compliance gates, and active incident hotfixes are always protected regardless of runner capacity.
If not yet registered: DM @devops-oncall with your repo name and workflow file path to complete registration in the service catalogue. Do this now — not during the next incident.
P1 — queued during Red, prioritised during Amber
This pipeline has elevated priority but does not qualify as P0
P1 pipelines queue ahead of standard workloads during both Amber and Red events, but they do not run during active Red load shedding. They will resume automatically as soon as capacity returns.
To request a P0 reassessment, open a DevOps service request with a written business justification. Do not contact oncall during an active Red event for classification queries.
  • Staging deploys ahead of a scheduled release window
  • Pipelines with next-business-day SLA obligations
  • Internal tooling deploys affecting multiple teams
P2 — standard queue, held during Red
This is a standard workload
P2 pipelines are held in queue during Red tier load shedding and resume automatically when capacity returns. Jobs are not lost — only delayed. No action is needed from your team.
Typical delay during Red events: queue hold time + up to 15–45 min drain time post-resolution. Plan your release timeline accordingly and avoid retriggering held jobs.
  • Feature branch CI, draft PR pipelines
  • Developer tooling, non-production environment deploys
  • Test runs and code quality scans with no SLA gate
The golden rule
P0 registration is a proactive process, not a reactive one. Pipelines are registered in the service catalogue during normal operations — not during Red events. If you believe a pipeline should be P0 but it isn't registered, raise a DevOps service request now.

During an active Red event, the oncall engineer's only job is stabilising the platform. Classification discussions happen after resolution.
