The load shedding analogy

Power utilities use load shedding — deliberately rotating which areas get power — when demand exceeds generation capacity. It's a controlled inconvenience that prevents a total grid collapse. Our GHA platform is facing the same pattern: constrained supply (on-prem runners) vs. unconstrained demand (all teams pushing simultaneously). The answer isn't more runners alone — it's demand shaping on the app side, just like utilities do.

Proposed: three-tier pipeline pressure system

Green — Normal
Runner pool <60% occupied. Standard SLA. All pipelines proceed as triggered.
Amber — Elevated
60–85% saturation. Non-critical pipelines queued. Teams notified via Slack/email. Discourage manual retriggers.
Red — Load shed
>85% saturation. Only P0 pipelines (prod deploys, security gates) run. All others held. Rolling window applied.

Status broadcast on a shared #devops-status Slack channel + optional GitHub status badge in repos. App teams opt into notifications per repo.

Pipeline best practices for app teams (demand shaping)

Use path filters on triggers. Don't run the full pipeline when only a README changes. paths and paths-ignore in your workflow file are free wins.
Collapse draft PRs. Disable CI on draft PRs or use pull_request: types: [ready_for_review] only. Avoid triggering full builds on every WIP commit.
Stagger large merges. Batch-merging feature branches at 09:00 Monday creates the equivalent of a power surge. Spread merges across the day.
Cancel redundant runs. Use concurrency: groups with cancel-in-progress: true so only the latest commit on a branch runs — not 5 stacked pushes.
Cache aggressively. Dependency installs that hit the network on every run waste runner time. actions/cache for node_modules, Maven, Gradle, pip etc. reduces per-job time significantly.
Split heavy pipelines. A 40-min monolithic pipeline blocks a runner longer than two 10-min pipelines with a gating step. Break long chains and use needs: dependencies wisely.
Don't manually retrigger under Amber/Red. If a pipeline fails during a congestion window, wait for status to return to Green before retriggering. Retriggers under load worsen the backlog.

What the DevOps team commits to in return

Proactive comms
Status updates pushed before users notice pain. Slack + email. Estimated resolution time included where known.
Visibility dashboard
Runner utilisation metrics visible to teams. Know when it's a good time to trigger large jobs.
P0 guarantee
Production deployments and security scanning gates are always protected — never shed, regardless of tier.
Vendor escalation
Where DB, VM, or runner issues require vendor involvement, DevOps owns the escalation path. App teams don't need to chase.
Why we can't just add runners As a financial institution on GitHub Enterprise Server (private), we cannot use GitHub's cloud runners. All runners are on-prem. Scaling requires infra procurement, security sign-off, and vendor co-ordination — not a same-day fix.
