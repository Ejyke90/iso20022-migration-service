Deep research: memory layers for personal grounding AI tools
Think of this as three chapters of a story. Chapter one: what the academic world knows about memory. Chapter two: what production systems have built. Chapter three: what it means specifically for PG.

Chapter one: the cognitive science foundation
The memory problem didn't start with AI. It started with how humans actually remember things — and the best AI memory designs are the ones that took that seriously.

The field has converged on four memory types formalized in the CoALA framework (Princeton, 2023), drawn from cognitive science: in-context working memory, episodic memory for past interactions, semantic memory for factual knowledge, and procedural memory for rules and skills. 
Atlan

Here's what each one means for a tool like PG:

Working memory is the active context window — what PG currently holds during a session. Your six-stage pipeline operates entirely here.

Episodic memory is "what happened." It stores time-stamped records of specific interactions — what the user said, what the agent did, what the outcome was. Unlike semantic memory, it preserves the sequence and context of events rather than abstracting them into general facts. For PG, this is the raw record of email threads, calendar events, and decisions made in context. 
Groundy

Semantic memory is "what I know." An episodic fact like "the user corrected the date format on Jan 5, Jan 12, and Feb 1" may consolidate into the semantic record "user prefers DD/MM/YYYY." This consolidation is rarely automatic; most current systems require explicit prompting or heuristic triggers. 
arXiv

The critical mechanism connecting them is consolidation. The canonical implementation is the reflection mechanism from Generative Agents (Park et al. 2023, Stanford). Periodically, the agent synthesizes recent episodes using a weighted combination of recency, relevance, and salience scores into higher-level semantic insights. The ablation evidence is striking: when the reflection mechanism was removed from the 25-agent simulation, emergent coordination behaviors disappeared entirely. 
Atlan

This consolidation gap is the most dangerous failure mode. The consolidation step — where episodes become semantic knowledge — is particularly underserved: it typically requires either explicit developer rules or periodic LLM-driven summarization, both of which are fragile and hard to validate. 
arXiv

For PG specifically, this means if you never consolidate, you end up with a growing pile of raw episodic signals (emails, calendar events) that are never distilled into the things that would actually make PG feel intelligent: "Ejike always prefers async over sync meetings," "Project X has been stalling since February," "This person's emails spike before quarter-end."

Chapter two: what production systems have built
MemGPT / Letta — the OS metaphor
The most influential architecture came from Stanford in 2023. The MemGPT architecture, described in "MemGPT: Towards LLMs as Operating Systems," treats the context window as RAM and external stores as disk — with explicit paging operations when memory exceeds the window limit. 
Groundy

Letta uses a three-tier model inspired by OS memory management: core memory (always in-context, like RAM), archival memory (external searchable vector store, like disk), and recall memory (conversation history). Procedural memory is architecturally unique: agents update their own operating instructions based on user feedback. 
Atlan

The implication for PG: the "always in-context" core memory tier is what should hold your user identity, active project summaries, and communication preferences — always loaded, always fresh.

Mem0 — production scale memory
Mem0 is currently the most widely deployed production memory layer. Mem0 is a scalable memory-centric architecture that dynamically extracts, consolidates, and retrieves salient information from ongoing conversations. It attains 91% lower p95 latency and saves more than 90% token cost, offering a compelling balance between advanced reasoning capabilities and practical deployment constraints. 
arXiv

Their architecture uses multi-scope tagging. Multi-scope memory is a design pattern where each memory write is tagged with one or more identity scopes: user_id for facts that persist across sessions, agent_id for facts tied to a specific agent instance, run_id or session_id for conversation-scoped facts, and app_id or org_id for shared organizational context. These scopes are composed at retrieval time, and the pipeline merges and ranks results automatically. 
Mem0

This scoping design maps cleanly to PG: a user_id for cross-project identity, a project_id for project-specific memory, and a session_id for ephemeral working context.

Zep / Graphiti — temporal knowledge graphs
The most technically ambitious production memory system. Zep is a novel memory layer for AI agents designed for enterprise-critical and dynamic environments. It centers on a temporally-aware knowledge graph engine, Graphiti, which systematically integrates and maintains both unstructured conversational data streams and structured business information, while representing the temporal validity and provenance of every fact. 
Emergent Mind

What makes Graphiti unique is the bi-temporal model. Every graph edge includes explicit validity intervals (t_valid, t_invalid). Graphiti uses semantic, keyword, and graph search to determine whether new knowledge conflicts with existing knowledge. When conflicts arise, Graphiti intelligently uses the temporal metadata to update or invalidate — but not discard — outdated information, preserving historical accuracy without large-scale recomputation. 
Neo4j

On the LongMemEval benchmark, Zep achieves up to 18.5% accuracy improvement and reduces response latency by 90% compared to baseline implementations. 
arXiv

For PG, this matters because emails and calendar events are inherently temporal. "John is the project lead" may have been true in January but false in March. A system that doesn't model time will confidently surface stale facts.

HiMeS (Tencent/WeChat) — closest analogue to PG
The most directly relevant research paper comes from Tencent. HiMeS is an AI-assistant architecture inspired by the hippocampus-neocortex memory mechanism that fuses short-term and long-term memory. A short-term memory extractor is trained to compress recent dialogue and proactively pre-retrieve documents from the knowledge base, emulating the cooperative interaction between the hippocampus and prefrontal cortex. A partitioned long-term memory network stores user-specific information and re-ranks retrieved documents, simulating distributed cortical storage and memory reactivation. 
arXiv

The key insight from HiMeS for PG: the short-term extractor doesn't just retrieve — it pre-retrieves based on where the conversation is heading. Applied to PG, this would mean the memory layer anticipates what a query is likely to need and surfaces it before the six-stage pipeline even runs.

MemMachine — the ground-truth preserving approach
MemMachine combines short-term memory, long-term episodic memory, and profile memory in a ground-truth-preserving architecture that stores raw conversational episodes and minimizes routine LLM-based extraction. Unlike episodic memory which preserves the raw record, semantic/profile memory distills high-level patterns: "the user prefers vegetarian restaurants," "the user works in financial services," or "the user's preferred communication style is concise and technical." 
arXiv

The "ground-truth preserving" principle is important: never lose the raw source. Summaries are always derived, never destructive.

On MongoDB as the memory store
MongoDB is very well positioned for this. MongoDB's native support for vector similarity search and traditional indexing within a single system eliminates the need for complex reference management across multiple databases, simplifying the coordination mechanisms that multi-agent architecture requires. 
MongoDB

The cognitive memory architecture integrates traditionally separate data concerns into a unified intelligence framework. Unified context means business entities serve as memory anchors, enriched with embeddings, conversation history, and behavioral patterns. Rather than scattering related information across multiple systems, all context remains accessible within cohesive document structures. 
MongoDB

MongoDB Atlas Vector Search extended to self-managed offerings in September 2025, so you can run this on your own infrastructure if needed. Organizations can now access vector search capabilities on MongoDB's local, on-premises, and self-managed offerings — important for organizations that need to keep data on their own infrastructure. 
MongoDB, Inc.

The one caution from enterprise practitioners: teams end up managing multiple databases — one for operational data, another for vector data, a third for conversation memory — each with different APIs and scaling characteristics. The recommendation is to choose a unified data architecture to reduce complexity from day one. 
MongoDB

MongoDB is the right answer to that caution — it is the unified architecture.

On Cohere embed v4 vs MongoDB's native embeddings
Keep Cohere. The research is clear on why. Mixing incompatible embedding spaces means you must fully migrate or maintain separate indexes — there is no partial compatibility. 
Getathenic

If memory chunks and email chunks live in different vector spaces, RRF cannot meaningfully compare their scores. Cohere Embed v4 supports mixed-modality inputs combining text and images into a single embedding, with a 128,000-token context window and compressed embedding types including float, int8, uint8, binary, and ubinary, facilitating efficient storage and faster retrieval. 
sourceforge

The 128K context window is specifically significant for your use case — an email thread or a calendar week can embed in a single pass without chunking distortion.

On markdown: the "boring files" philosophy
There's a genuinely interesting counter-current in the literature — serious practitioners arguing for markdown over databases for personal-scale memory. The simplest memory storage is the file system: markdown files in hierarchical folders. File-based memory works well at small scale and for individual users, but it lacks indexing, structured queries, and efficient similarity search. As memory grows to thousands of entries across many users, retrieval degrades and governance becomes difficult to enforce. 
Databricks

However, the "Markdown" approach is optimal for Local Agents because the context is finite and structured. The "Database" approach is optimal for Enterprise Agents where the memory consists of millions of user profiles and history logs that cannot fit into a single file, requiring dynamic agent management and more sophisticated search capabilities. 
DEV Community

The emerging pattern is a hybrid: markdown files are always the source of truth — the vector database is a rebuildable shadow index. Plugins append to markdown files, which remain human-editable; a file watcher automatically re-chunks and re-indexes on change. 
GitHub

This is the right model for PG: markdown as the canonical human-readable memory record, MongoDB as the queryable index. You get transparency, portability, and performance together.

On single file vs. multi-file
The single-file approach collapses under its own weight. As foundation models converge in capability, the differentiator for enterprise agents will increasingly be what memory they have accumulated rather than which model they call. That accumulation demands structure. 
Databricks

The split should be semantic, not temporal. Based on how your whiteboard defines a Project entity (active content, past events, roadmap, summary), the natural document hierarchy is:

One user identity document (communication style, preferences, relationship graph)
One project memory document per active project (timeline, decisions, summaries)
One archive document per completed project
A daily episodic log (time-bounded, eventually consolidated or expired)
On co-location vs. separate memory service
The tradeoff is predictable. Centralized memory gives you strong consistency and simple implementation, but it creates bottlenecks. As you add more agents, a single shared store becomes a point of contention and a single point of failure. 
Mem0

Multi-agent systems fail for structural reasons: context degrades across agents, errors propagate through shared interactions, and state diverges when nothing enforces consistency. Memory engineering provides that infrastructure through a coherent taxonomy of memory types, persistence with explicit lifecycle rules, retrieval tuned to agent access patterns, coordination that defines clear sharing boundaries, and consistency that maintains shared truth under concurrent updates. 
O'Reilly

The recommendation: a thin separate memory service exposed as an MCP tool. It presents three clean operations — write(memory_unit), read(query, scope), consolidate(project_id) — and the PG MCP calls it as channel 3 alongside dense and metadata search, injected before RRF fusion.

For the memory orchestration layer you mentioned, in complex multi-agent architectures, simultaneous read and write operations across a shared database dramatically worsen memory conflicts. To prevent race conditions and cross-agent contamination, systems must implement strict shared-memory access controls. 
Analytics Vidhya

The agent design that follows from this: a writer agent (passive, writes memory on every ingestion cycle), a consolidation agent (scheduled, converts episodic → semantic), a retrieval agent (on-demand, fetches and ranks relevant memory for each query), and a decay/expiry agent (periodic, archives or deletes stale signals). Each agent operates on a different time horizon — retrieval is synchronous, consolidation is nightly, decay is weekly.

On the three-layer memory model for PG specifically
Putting it together as a coherent stack:

Layer 0 (raw): Your existing six-stage pipeline. Emails, calendar, documents — all embedded with Cohere, indexed in SQLite/S3. This layer doesn't change.

Layer 1 (episodic): Per-session and per-day logs stored as markdown documents, indexed in MongoDB with Cohere vectors. Time-scoped. Written by the writer agent after each interaction. This is where "Ejike queried about Project X three times this week" lives.

Layer 2 (semantic/profile): Distilled facts about the user, their projects, and their relationships. MongoDB documents with structured schema. Written by the consolidation agent. This is where "Ejike's communication style is direct, prefers bullet summaries, and is lead on Project X" lives.

Layer 3 (procedural): System-level preferences — how PG should behave. Likely a static markdown file at first, updated manually or by a dedicated preference-learning agent.

The one unresolved question
Everything above assumes memory is additive. But PG ingests emails that may contradict each other, calendar events that get cancelled, and documents that get superseded. The research community calls this the knowledge conflict problem.

Zep's bi-temporal model is the best current answer — tracking both when something was true in the world and when PG learned about it. Without that, the memory layer will confidently surface stale facts as current truth.

This is likely the first design question to resolve before writing any code. How PG handles "the meeting was cancelled" — does it delete the memory, mark it invalid, or create a new memory that supersedes the old one — determines everything downstream.
